# upstream 동기화 리뷰

yc(T3 Code 개인 빌드) 저장소에 upstream stable 태그를 merge한 커밋이 `HEAD`에 있습니다. 타입 검사와 개인 기능 테스트는 이미 돌았습니다. 당신은 테스트가 놓치는 문제, 즉 개인 기능이 조용히 망가졌는지를 찾는 리뷰어입니다. 코드는 고치지 않습니다.

먼저 `PERSONAL.md`의 "유지할 개인 기능"을 읽습니다. 각 `###` 항목이 점검할 기능 하나입니다.

## 자료

"이번 작업"에 적힌 파일을 읽습니다.

- `patch-before.diff`: 동기화 전, 이전 upstream 태그 위에 얹혀 있던 yc 변경
- `patch-after.diff`: 동기화 후, 새 upstream 태그 위에 얹힌 yc 변경
- `upstream-overlap.diff`: 두 태그 사이에 upstream이 바꾼 내용 중 yc 변경과 같은 파일에 있는 부분

두 패치를 비교하면 yc 변경이 merge로 어떻게 달라졌는지 보입니다. overlap diff는 그 주변에서 upstream이 무엇을 바꿨는지 보여 줍니다. 필요하면 저장소의 현재 코드를 직접 읽고 호출 관계를 따라갑니다.

## 점검 방법

기능마다 서브에이전트를 하나씩 띄워 병렬로 점검합니다. 전체 시간 제한은 40분입니다. 각 기능에 대해 아래를 확인합니다.

1. 진입점에서 실제로 닿는가: 화면, 설정, 단축키 등 사용자가 기능을 쓰는 경로가 지금 코드에서도 그 기능까지 이어지는지 확인합니다. 우리가 넣은 연결 코드가 더는 렌더링되거나 호출되지 않는 경로에 남아 있지 않은지 봅니다.
2. upstream이 주변 동작을 바꿨는가: 기능이 기대는 컴포넌트, 상태, 설정, 계약이 바뀌어 동작이나 모양이 달라질 수 있는지 봅니다.
3. 패치에서 빠지거나 바뀐 부분이 의도된 것인가: `patch-before.diff`에 있던 변경이 `patch-after.diff`에서 사라졌거나 달라졌다면 그 이유를 확인합니다.

확인하지 못한 것은 정상으로 적지 않습니다.

## 보고 파일

"이번 작업"에 적힌 보고 파일 경로에 아래 형식의 JSON을 씁니다. `features`에는 `PERSONAL.md`의 `###` 제목을 그대로 `name`으로 써서 모든 기능을 넣습니다.

```json
{
  "features": [{ "name": "Context ring", "status": "ok", "note": "한 줄 근거" }],
  "summary": "- 눈여겨볼 변경을 한국어 Markdown 목록으로"
}
```

- `status`: `ok`(진입점부터 연결을 확인함), `suspect`(깨졌을 수 있거나 확인하지 못함), `broken`(깨짐)
- `note`: 판단 근거를 한국어 한 줄로 씁니다. 파일과 심볼 이름을 넣습니다.
- `summary`: 기능 점검 밖에서라도 사람이 알아야 할 변경이 있으면 적습니다. 없으면 빈 문자열입니다.
